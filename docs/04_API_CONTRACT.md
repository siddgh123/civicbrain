# 04 — API Contract (REST, JSON, base path `/api/v1`)

Conventions (apply to every endpoint):
- JSON camelCase; timestamps ISO-8601 with offset (`2026-10-05T08:20:00+05:30`); IDs are numbers; the citizen-facing complaint number is `publicRef` (`CB-000123`).
- Auth: `Authorization: Bearer <accessToken>` except `/auth/*` and `/public/*`. Refresh uses the `__Host-cb_rt` cookie + header `X-CB-CSRF: 1`.
- Errors: RFC 9457 Problem Details with `code`, `requestId`, optional `fieldErrors[]` — full list in `12_ERROR_HANDLING.md`.
- Lists: `?page=0&size=20&sort=field,dir` (size ≤ 100) → `{ "items": [...], "page": 0, "size": 20, "totalItems": 57, "totalPages": 3 }`.
- Ownership failures return **404 NOT_FOUND** (never reveal that the object exists).
- Every mutating endpoint writes `audit_logs` (actor, entity, old/new JSON without secrets).
- The OpenAPI document is generated by springdoc at `/v3/api-docs` and snapshot-tested; this file and the snapshot must agree.

## 1. Auth — `/auth` (public, rate-limited)
| Method & path | Body | Success | Notes |
|---|---|---|---|
| POST `/auth/register` | `{fullName, email, phone, password, privacyNoticeVersion, consents:{whatsapp, publicPhoto, aiTraining}}` | 202 `{otpId, expiresInSec}` | Always 202 and never 409: if the e-mail **or** phone already exists, nothing is created, the owner gets a "someone tried to register" mail and the response carries a decoy `otpId` (a real `auth_otp_codes` row with `user_id` NULL whose code is never sent). Otherwise creates the CITIZEN with `email_verified_at = NULL`; login is refused with 403 `EMAIL_NOT_VERIFIED` (+ new `otpId`) until the OTP is verified. |
| POST `/auth/verify-otp` | `{otpId, code}` | 200 `{verified:true}` | 5 attempts, 10 min. |
| POST `/auth/resend-otp` | `{otpId}` | 202 | 1 per 60 s per destination. |
| POST `/auth/login` | `{identifier, password}` (e-mail or +91 phone) | 200 `{accessToken, expiresIn, user}` + cookie, or 200 `{mfaRequired:true, mfaToken}`, or 200 `{mfaSetupRequired:true, mfaToken}` | `user = {id, fullName, role, mustChangePassword, preferredLanguage}` |
| POST `/auth/mfa/setup` | `{mfaToken}` | 200 `{otpauthUri, secretBase32}` | OFFICER/ADMIN first login; QR shown in UI. |
| POST `/auth/mfa/confirm` | `{mfaToken, code}` | 200 tokens + cookie | Enables TOTP. |
| POST `/auth/mfa/verify` | `{mfaToken, code}` | 200 tokens + cookie | Rejects a code step already used. |
| POST `/auth/refresh` | — (cookie + `X-CB-CSRF`) | 200 `{accessToken, expiresIn}` + rotated cookie | Reuse of a rotated token revokes the family → 401. |
| POST `/auth/logout` | — (cookie + `X-CB-CSRF`) | 204 | Revokes family, clears cookie. |
| POST `/auth/logout-all` | — (bearer, **authenticated** despite the `/auth` prefix) | 204 | Sets `token_valid_after = now()`; `auth_events` LOGOUT_ALL. |
| POST `/auth/password/forgot` | `{email}` | 202 `{otpId, expiresInSec}` always | Unknown e-mail → decoy `otpId` (same shape and timing; code never sent). |
| POST `/auth/password/reset` | `{otpId, code, newPassword}` | 204 | Revokes all sessions. |
| POST `/auth/password/change` | `{currentPassword, newPassword}` (bearer, **authenticated**) | 204 | Clears `mustChangePassword`; revokes other sessions. |

## 2. Me — `/me` (any authenticated user)
`GET /me` → `{id, fullName, email, phoneMasked, role, preferredLanguage, emailOptIn, whatsappOptIn, consents:[{type, granted, noticeVersion, at}]}` · `PUT /me {fullName, preferredLanguage, emailOptIn, whatsappOptIn}` · `POST /me/consents {consentType, granted}` · `POST /me/privacy-requests {requestType, details}` → 201 · `GET /me/export` → JSON of own data · `GET /me/notifications?page` (in-app list).

## 3. Public — `/public` (no auth, cached 60 s)
`GET /public/categories` → `[{id, name, workTypeCode, citizenSelectable, needsDepthAnswer}]` — every active category (officer screens name all 8 on existing complaints); the citizen wizard shows only `citizenSelectable: true` (MVP, V6: Pothole, Road Damage, Waterlogging, Garbage Accumulation, Other) · `GET /public/wards` → GeoJSON (simplified 5 m) with `wardNumber` · `GET /public/map?bbox=minLon,minLat,maxLon,maxLat&category=&status=` → GeoJSON from `v_public_complaint_map` (synthetic rows only when `app.demo.show-synthetic=true`) · `GET /public/privacy-notice` → current notice · `GET /public/media/{token}` → one photo for a signed token (HMAC, valid 10 min), used only to send a WhatsApp photo through Twilio.

## 4. Files and client errors
`POST /client-errors {message, stack?, url, portal}` (authenticated or anonymous, 10/min per IP) → 204; written only to the structured server log (message truncated to 2,000 chars, no PII, no DB row).
`GET /files/{imageId}` → image bytes (`Cache-Control: private, max-age=300`) if the caller may see the complaint (owner, officer in scope, assigned contractor, admin); `GET /public/files/{imageId}` → blurred copy only if `public_approved`.

## 5. Citizen — `/citizen` (CITIZEN, e-mail verified)
| Method & path | Request | Success |
|---|---|---|
| POST `/citizen/capture-sessions` | — | 201 `{captureSessionId, expiresAt}` |
| POST `/citizen/complaints` | multipart: `data` (JSON) + `photo` (JPEG/PNG ≤ 8 MB) | 201 `{complaintId, publicRef, status, wardNumber}` |
| GET `/citizen/complaints` | `?page&size&status` | 200 list `{complaintId, publicRef, title, categoryName, status, wardNumber, submittedAt, thumbnailImageId}` |
| GET `/citizen/complaints/{id}` | — | 200 `{…, description, landmark, latitude, longitude, images:[{imageId, role}], timeline:[{status, at, remarks}], contractorName?, plannedDate?, mergedIntoPublicRef?, canGiveFeedback}` |
| POST `/citizen/complaints/{id}/feedback` | `{isResolved, rating?, comment?}` | 201; `isResolved=false` on COMPLETED/CLOSED → REOPENED. One row per (complaint, user): a second answer (e.g. after a reopen) **updates** the row; the previous values go to `audit_logs`. 422 `FEEDBACK_NOT_ALLOWED` in other statuses. |
| POST `/citizen/support/{publicRef}` | — | 204 (one UP vote) · DELETE same path → 204 |

`data` for a complaint: `{categoryId, title, description, landmark?, latitude, longitude, locationAccuracyM, locationCapturedAt, devicePitchDeg?, deviceRollDeg?, captureSessionId, captureMethod: "IN_APP_CAMERA"|"FILE_CAPTURE", a4InFrame: boolean, depthAnswer?: "SHALLOW"|"FINGER"|"DEEP"}`. Stored in `complaints.a4_in_frame`, `complaints.depth_answer` (V5); pitch/roll/accuracy on the `complaint_images` row. `depthAnswer` is required when the category has `needs_depth_answer` (Pothole, Waterlogging) and must be absent otherwise (400 `VALIDATION_FAILED` with a field error on `depthAnswer`). `categoryId` must be an active category with `citizen_selectable = true` (MVP, V6: not Water Leakage, Blocked Drain, Streetlight); an unknown or non-selectable one → 400 `VALIDATION_FAILED` with a field error on `categoryId` (code `INVALID_VALUE`), nothing stored.
Server validation order (first failure wins): auth & e-mail verified → rate limit (5/24 h) → JSON schema → capture session (own, unused, not expired) → accuracy ≤ 150 m → `locationCapturedAt` within 10 min of server time → inside boundary (`fn_locate_point`) → file magic bytes/size/dimensions (≥ 320 px) → store file → DB transaction.

## 6. Officer — `/officer` (OFFICER within scope, ADMIN all)
Complaints: `GET /officer/complaints?tab=NEW|NEEDS_REVIEW|IN_PROGRESS|COMPLETED|REJECTED&wardNumber&categoryId&workType&priorityLevel&authenticity=PASSED|FLAGGED&from&to&includeSynthetic=false&page&size&sort` (from `v_officer_complaint_queue`: NEW = `dashboard_tab` NEW; NEEDS_REVIEW = NEW rows with `ai_status` FAILED, `authenticity_status` FLAGGED or `duplicate_status` UNCERTAIN, plus SUBMITTED rows older than 10 min; REJECTED = `dashboard_tab` CLOSED_OUT and status REJECTED; merged children are never listed, they appear inside their master) · `GET /officer/complaints/geojson?…same filters` · `GET /officer/complaints/{id}` (full detail: images, detections, measurements AI vs contractor, estimate lines, priority factors + explanation, authenticity checks, duplicates, timeline, inspection, completion) · `GET /officer/stats` (counts per tab, ward, category).
Actions (each needs `reason`/`remarks`, returns the updated detail): `POST …/{id}/reject {reason}` · `POST …/{id}/merge {masterComplaintId, reason}` · `POST …/{id}/unmerge {reason}` · `PATCH …/{id}/category {categoryId, reason}` · `POST …/{id}/estimate-override {workersRequired, durationHours, totalCostExpected, reason}` · `POST …/{id}/reanalyze` → 202 · `POST …/{id}/accept {remarks}` (SUBMITTED → VERIFIED when the analysis failed or is stuck) · `POST …/{id}/restore {reason}` (REJECTED → VERIFIED) · `POST …/{id}/remove-from-plan {reason}` (SCHEDULED/ASSIGNED/INSPECTED → VERIFIED; the database frees the complaint and marks the plan item REMOVED, V5) · `POST …/{id}/verify-completion {approved, remarks}`.
Public photos: `POST /officer/images/{imageId}/blur {rects:[{x,y,w,h}]}` (stored-image pixels, ≤ 20 rectangles for plates etc.) → 202, enqueues BLUR_IMAGE with the rectangles in `jobs.payload` · `GET /officer/images/{imageId}/blurred` → JPEG preview (404 until ready) · `POST /officer/images/{imageId}/public-approval {approve}` → 409 `BLUR_NOT_READY` if no blurred copy, 422 `CONSENT_MISSING` if the owner has no current PUBLIC_PHOTO consent.
Duplicates: `GET /officer/duplicates/review-queue` · `POST /officer/duplicates/{relationId}/decision {decision: MERGE|KEEP_SEPARATE, comment}`.
Plans: `POST /officer/plans/generate {plannedDate, workTypeCode, wardNumbers?, complaintIds?, contractorIds?}` → 202 `{runId}` · `GET /officer/optimizer-runs/{runId}` → `{status, actionPlanIds, droppedJobs:[{complaintId, publicRef, reason}], error?}` · `GET /officer/plans?status&date&page` · `GET /officer/plans/{id}` → `{id, planCode, version, status, plannedDate, workTypeCode, contractor?, totals:{jobCount, workers, serviceHours, travelHours, distanceKm, cost}, items:[{complaintId, publicRef, sequenceNo, plannedStart, plannedEnd, estWorkers, estCost, lat, lon}], routeGeoJson, revisions:[{version, changedBy, at, summary}]}` · `PUT /officer/plans/{id} {version, plannedDate, items:[{complaintId, sequenceNo}], notes}` → 202 `{runId}` (worker re-times with the fixed order; 409 `STALE_VERSION` if `version` is old) · `POST /officer/plans/{id}/approve` · `POST /officer/plans/{id}/assign {contractorId}` · `POST /officer/plans/{id}/cancel {reason}` · `GET /officer/plans/{id}/export.pdf?version=` · `GET /officer/plans/{id}/export.xlsx?version=`.
**Plan lifecycle:** DRAFT → APPROVED (`fn_approve_action_plan`) → ASSIGNED (`fn_assign_action_plan`) → IN_PROGRESS (backend, when the first item's complaint becomes INSPECTED) → COMPLETED (backend, when every ACTIVE item's complaint is COMPLETED or CLOSED — re-checked after every status change of an item's complaint, including when a complaint leaves the plan through REOPENED or remove-from-plan and the V5 trigger marks its item REMOVED; a plan whose items are all REMOVED becomes CANCELLED). `PUT` (edit) only on DRAFT, otherwise 409 `PLAN_STATE_CONFLICT`. CANCELLED only from DRAFT/APPROVED/ASSIGNED; 409 `PLAN_STATE_CONFLICT` if any ACTIVE item's complaint is IN_PROGRESS or COMPLETED; cancelling APPROVED/ASSIGNED moves each ACTIVE item's complaint back to VERIFIED in the same transaction (the V5 trigger frees it and marks the item REMOVED). An inspection with `issueConfirmed=false` still moves the complaint to INSPECTED; the officer sees "issue not found" and may use remove-from-plan and then reject. The DB rule REOPENED → ASSIGNED is not used by the API (a reopened complaint goes through a new plan). Contractor access (§7) always requires an ACTIVE item in an ASSIGNED/IN_PROGRESS plan of the caller's firm, so a firm loses access as soon as the item is REMOVED.
Contractors: `GET/POST /officer/contractors` · `GET/PUT /officer/contractors/{id}` · `POST /officer/contractors/{id}/status {status}` · `GET/POST /officer/contractors/{id}/workers` · `PUT/DELETE /officer/contractors/{id}/workers/{workerId}` · `PUT /officer/contractors/{id}/equipment [{equipmentCode, quantity}]`. Creating a contractor creates a CONTRACTOR user with a one-time password shown once and `must_change_password = true`.
Notifications: `GET /officer/notifications?complaintId&channel&status&page`.

## 7. Contractor — `/contractor` (CONTRACTOR: own firm; CONTRACTOR_STAFF: own firm's active plans)
`GET /contractor/worklist?date=` (from `v_contractor_worklist`) · `GET /contractor/plans/{id}` · `GET /contractor/complaints/{id}` (only if the complaint has an ACTIVE item in an ASSIGNED/IN_PROGRESS plan of the caller's firm; no citizen phone/e-mail; the same check guards inspection/start/completion) · `POST /contractor/capture-sessions` · `POST /contractor/complaints/{id}/inspection` multipart `data {issueConfirmed, findings, lengthM?, widthM?, depthM?, expectedCompletionDate, latitude, longitude, accuracyM, captureSessionId}` + `photos` (1–3) → 201 (status INSPECTED) · `POST /contractor/complaints/{id}/start` → 200 (IN_PROGRESS) · `POST /contractor/complaints/{id}/completion` multipart `data {workSummary, actualWorkers, actualHours, actualCost?, materialsUsed:[{materialCode, quantity, unit}], latitude, longitude, accuracyM, captureSessionId}` + `photos` (1–3) → 201 (COMPLETED).

## 9. Webhooks (no bearer; signature required)
`GET /webhooks/meta` (hub.verify_token challenge) · `POST /webhooks/meta` (verify `X-Hub-Signature-256` HMAC with app secret, constant-time) · `POST /webhooks/twilio` (verify `X-Twilio-Signature`). Unknown/invalid signature → 401, logged.

## 10. AI service (127.0.0.1:8001 only)
`GET /health` → `{status, db, osrm, modelsLoaded, models}` (`models` = per required model file, by its `MANIFEST.json` name: `"ok"` = present with the listed SHA-256, else the problem, e.g. `"folder missing"`; checked once at start, P08) — **no auth** (bound to localhost; used by `start-e2e.ps1` and the admin page) · `GET /v1/models` → `{yolo:{file, sha256, classes}, classifier:{version}, embedding:{name}}` and `POST /v1/jobs/{jobId}/requeue` — service JWT (HS256 `AI_SERVICE_JWT_SECRET`, `iss=civicbrain-api`, `aud=civicbrain-ai`, 60 s). The backend's `POST /admin/jobs/{id}/requeue` inserts a new QUEUED job row itself (no call needed); the AI endpoint exists for manual use.

## 11. Rate limits (Bucket4j, key = IP + account/destination)
| Endpoint | Limit |
|---|---|
| `/auth/login` | 30 / 15 min per identifier, 100 / 15 min per IP (above the 10-failure lockout, so the lockout is observable) |
| `/auth/register`, `/auth/password/forgot` | 5 / hour per IP |
| OTP send/resend | 1 / 60 s and 5 / hour per destination |
| OTP/TOTP verify | 5 attempts per code; 20 / hour per account |
| `POST /citizen/complaints` | 5 / 24 h per user, 20 / hour per IP |
| Everything else authenticated | 300 / min per user |
Exceeded → 429 `RATE_LIMITED` + `Retry-After`. All limits are properties `app.rate-limits.*`; the `e2e` profile multiplies per-IP limits × 100 and allows 100 complaints / 24 h per user (Playwright runs from one IP). Buckets are in memory (reset on backend restart).
