# 03 — Database

PostgreSQL 18 + PostGIS 3.6, database `civicbrain`, schema `public`, SRID 4326 everywhere. The full schema after all migrations is in `db/SCHEMA_REFERENCE_after_V5.sql` (V6 changes data only) (74 application tables + PostGIS `spatial_ref_sys`; 6 application views + 2 PostGIS views) — read it before writing any entity or query.

- `db/` versions have `BEGIN/COMMIT` (for pgAdmin/psql). `flyway/` versions are identical without the outer transaction (Flyway wraps each migration) → copy them to `backend/src/main/resources/db/migration/`. `scripts/ci/check-migrations.sh` (CI) fails if the three copies drift.
- **Roles first:** `db/tools/create_roles_template.sql` creates the two login roles once per PostgreSQL server (passwords = `DB_PASSWORD` / `DB_AI_PASSWORD` from `.env`; `scripts/dev/db-rebuild-test.ps1` does it for you). Then any migrate applies `R__civicbrain_grants.sql` automatically.
- **Main dev database `civicbrain`, restored from civicbrain_backup:** let **Flyway** apply V2–V6 + R__ on the first backend start (`baseline-on-migrate: true`, `baseline-version: 1` → V1 is skipped). Do **not** also run V2–V5 by hand in pgAdmin on this database. If someone already did, set `spring.flyway.baseline-version` to the highest version they ran (e.g. 5) for the first start only (then those are not re-applied), and remove it after the history table exists.
- **Empty database (new laptop without the backup, `civicbrain_e2e`, Testcontainers):** Flyway runs V1–V6 + R__; optional demo data: `db/seed/seed_synthetic_demo_data.sql` (as superuser).
- **`civicbrain_test`** is built by `scripts/dev/db-rebuild-test.ps1` with psql from the same `flyway/` files (identical to what CI does) + seed. It has no Flyway history table, so **the backend never connects to it**; it serves the SQL tests and the AI integration tests.
- Never edit an applied migration. New change = next free number, e.g. `V7__<name>.sql` (+ test SQL in `db/tests/`). Flyway placeholders are disabled (`spring.flyway.placeholder-replacement=false`).

## 3. Rules the code must respect
1. **Status changes** only through an UPDATE of `complaints.status` after setting `civicbrain.actor_user_id`, `civicbrain.actor_role`, optional `civicbrain.status_remarks` (transaction-local). The trigger validates the move, stamps `closed_at`, writes history and the outbox. Invalid move → SQLSTATE 23514 (check_violation) → API 409 `INVALID_TRANSITION`; wrong role → 42501 → 403 `ROLE_NOT_ALLOWED`.
2. **New complaints** must be inserted with status SUBMITTED and `is_synthetic = false` (default). The insert enqueues the analysis job automatically — do not enqueue it again in Java.
3. **Plans:** approve with `SELECT fn_approve_action_plan(:planId, :officerUserId)`, assign with `SELECT fn_assign_action_plan(:planId, :contractorId, :officerUserId)`. Do not reimplement them in Java.
4. **Duplicates:** children have `master_complaint_id` set and status MERGED. Never filter children by `duplicate_status` (masters carry DUPLICATE too).
5. **Wards:** always join `complaints.ward_id = wards.ward_id`; show `wards.ward_number`. (`pois.ward_id` was wrong in the original data — V3 fixed it; any future import must store `ward_id`.)
6. **Geography:** distances/areas with `::geography` (metres); `ST_DWithin(a::geography, b::geography, m)`. There is a GIST index on `(location::geography)`.
7. **One current row:** `priority_assessments` and `resource_estimates` allow one `is_current = true` per complaint (partial unique index) — set the old one false in the same transaction.
8. **Jobs:** worker uses only `fn_claim_jobs`, `fn_finish_job`, `fn_requeue_stale_jobs`.
9. **Time:** all timestamps `timestamptz` (UTC internally, displayed Asia/Kolkata) — except `action_plan_items.planned_start/end` and `action_plans.planned_start/end`, which are local Asia/Kolkata wall-clock values (`timestamp`/`time` without zone → `LocalDateTime`/`LocalTime`).
10. **Leaving a plan (V5 trigger `trg_complaints_status_release`):** REOPENED, or VERIFIED from SCHEDULED/ASSIGNED/INSPECTED, clears `current_action_plan_id` and `assigned_contractor_id`. The plan item becomes REMOVED for the VERIFIED case, and for REOPENED while that plan is still ASSIGNED/IN_PROGRESS (so the plan can complete and the old firm loses access); a COMPLETED plan keeps the item as history. Do not re-implement this in Java; after any such change the backend re-evaluates the plan's completion (`04_API_CONTRACT.md` §6). The status moves themselves (20 rules) are in `complaint_status_transitions`: SUBMITTED→VERIFIED/MERGED/REJECTED (SYSTEM, OFFICER, ADMIN) · VERIFIED→SCHEDULED/MERGED/REJECTED · SCHEDULED→ASSIGNED/VERIFIED · ASSIGNED→INSPECTED (CONTRACTOR, STAFF) / VERIFIED · INSPECTED→IN_PROGRESS (CONTRACTOR, STAFF) / VERIFIED · IN_PROGRESS→COMPLETED (CONTRACTOR, STAFF) · COMPLETED→CLOSED (OFFICER, ADMIN, SYSTEM) / REOPENED (OFFICER, ADMIN, CITIZEN) · CLOSED→REOPENED (OFFICER, ADMIN, CITIZEN) · REOPENED→SCHEDULED/ASSIGNED · MERGED→VERIFIED · REJECTED→VERIFIED (officer moves are OFFICER, ADMIN).
11. **Fixed value lists** (CHECK constraints — use exactly these): `auth_events.event_type` incl. V5's TOTP_ENABLED/TOTP_VERIFIED/TOTP_FAILED/TOTP_RESET/LOGOUT_ALL; `audit_logs` needs `entity_id` **or** `entity_key` (V5, for things keyed by a code such as rates); `defect_measurements.method` GROUND_PLANE_HOMOGRAPHY / REFERENCE_OBJECT / MONOCULAR_DEPTH / CATEGORY_DEFAULT / MANUAL_TAPE; `resource_estimates.estimate_source` AI_MODEL / RULE_BASED / STEP10_PRECOMPUTED / CONTRACTOR_INSPECTION / OFFICER_OVERRIDE; `notifications.provider` GMAIL_SMTP / BREVO / RESEND / META_CLOUD_API / TWILIO_SANDBOX / INTERNAL; `jobs.job_type` ANALYZE_COMPLAINT / ANALYZE_IMAGE / OPTIMIZE_PLAN / BLUR_IMAGE / RENDER_EXPORT; `jobs.max_attempts` default 3 (retries after 1 and 5 min, then DEAD). Mapping rules: `06_AI_PIPELINE.md` §2.4–2.5, `02_ARCHITECTURE.md` §5.
12. The V4 column comment on `users.totp_secret_enc` named an old variable; V5 corrected it — the key is `TOTP_ENC_KEY`.

## 5. Database roles (create once, P1)
`db/tools/create_roles_template.sql` creates `civicbrain_app` (Spring) and `civicbrain_ai` (worker); `R__civicbrain_grants.sql` gives them their rights in every database: app = SELECT/INSERT/UPDATE/DELETE on application tables, no DDL, INSERT+SELECT only on the append-only logs (`audit_logs`, `auth_events`, `complaint_status_history`, `ward_*` logs), read-only on reference data and `step13_*`; ai = SELECT on everything, INSERT/UPDATE/DELETE on AI tables, jobs, optimizer runs and plans, UPDATE on complaints/images/users, INSERT on history/outbox/audit. `fn_purge_expired()` is SECURITY DEFINER so the app can run retention without DELETE on `auth_events`. Flyway runs as the database owner (`PG_ADMIN_USER`, `postgres` in local dev). Never connect the app or the worker as `postgres`. A new migration that adds an append-only or reference table must add it to the REVOKE lists in `R__civicbrain_grants.sql` (all copies); every new table must be added to the wipe or keep list of `db/tools/e2e_reset.sql` (the script stops on unclassified tables). If Flyway ever ran R__ before the roles existed, run `db/R__civicbrain_grants.sql` once by hand on that database — Flyway re-applies a repeatable migration only when the file changes (`start-backend.ps1` refuses to start without the roles to prevent this).

## 6. Backups
Daily during the build: `scripts/dev/backup-db.ps1` (`pg_dump -Fc` → `backups/civicbrain_yyyyMMdd_HHmm.backup`, checked with `pg_restore --list`, keeps 14 days, `-CopyTo` for a USB stick). Test a restore into `civicbrain_restore_test` once per phase and run `db/tests/test_V4.sql` there.
